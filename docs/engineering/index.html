Project

Engineering

This page focuses on the work behind the features: observed failure modes, the evidence used to isolate them, the implemented change, and the result that can be supported by the repository history.

Display performance

Problem
The ESP-IDF Sharp driver was configured for 2 MHz. A worst-case 400 × 240 transfer took about 49 ms on the wire, making a 30 FPS Game Boy presentation path impossible.
Investigation
Driver timing was compared with the stable Arduino firmware on the same board. Serial performance logs separated emulator rate, LCD rate, and frame time instead of treating them as one FPS value.
Solution
The display bus was restored to 14 MHz. Dirty-row transfers stayed enabled; framebuffer scans and DMA staging were kept in internal memory where possible; full-screen output received a direct fast path.
Result
Worst-case transfer time fell to roughly 7 ms on the wire. The STEP9.5 baseline records approximately 29.9 visible LCD updates per second during full-speed Game Boy emulation.

Game Boy emulator optimization

Problem
Large ROMs executing from PSRAM could advance too slowly. One measured regression reported emu=39, lcd=31, and frame time around 26 ms; automatic frame skipping could make a slow game look even slower.
Investigation
Once-per-second diagnostics tracked emulated frames, presented frames, ROM location, cache hits and misses, cache-fill time, audio state, heap state, and I²C errors. The data showed that LCD rate and Game Boy CPU rate were different bottlenecks.
Solution
CPU, timers, interrupts, joypad, and APU writes now run for every 59.7 Hz Game Boy frame while expensive LCD scanline drawing is skipped on alternate frames. Larger PSRAM ROMs use an adaptive internal 16 KiB-page cache with bank 0 pinned and LRU replacement.
Result
The documented performance baseline is full-rate 59.7 Hz Game Boy emulation with approximately 29.9 Hz LCD presentation, including ROMs that do not fit entirely in internal memory.

Memory, PSRAM, and internal RAM

Problem
ROM data benefits from the 8 MB PSRAM, but latency-sensitive framebuffers, DMA buffers, task stacks, and cache pages compete for limited internal memory. A single 256 KiB early arena request could fail completely and leave arena=0.
Investigation
Heap diagnostics recorded total free internal RAM, largest contiguous block, PSRAM location, and cache-page availability. The three original 160 × 144 shade buffers also accounted for 69,120 bytes.
Solution
Four Game Boy shades are packed at 2 bits per pixel, reducing one frame from 23,040 to 5,760 bytes and three buffers to 17,280 bytes. The firmware reserves the largest 16 KiB-aligned internal arena up to 128 KiB while leaving 128 KiB of headroom.
Result
The packed framebuffers save 51,840 bytes. ROMs that fit use the arena directly; larger ROMs keep bulk data in PSRAM and reuse the arena as a two-to-eight-page bank cache.

Audio buffering

Problem
Generating one APU packet inside each video frame made slow rendering starve audio. An adaptive playback rate could conceal a draining buffer, but it also changed pitch.
Investigation
The implementation was compared with the stable Arduino path, and underrun/overflow counters were added to the performance line. The stable design used a dedicated high-priority Core 0 producer paced by blocking I²S output.
Solution
MiniGB APU and MAX98357A stay locked to 32,768 Hz. A priority-7 Core 0 APU task feeds an internal ring buffer; the priority-8 I²S writer consumes at the hardware clock. Underruns fade out and back in without stretching playback.
Result
Audio timing is decoupled from the visible frame rate and the runtime no longer changes playback speed to hide missed deadlines. The fixed-rate path is retained in the current baseline.

FreeRTOS task and core organization

Problem
Emulation, I²S, display work, input, motion, and system UI have different latency requirements. Running them without clear ownership risks audio underruns, input lag, and watchdog starvation.
Investigation
Serial diagnostics and acceptance tests tracked frame deadlines, audio counters, task watchdog faults, and I²C errors. The emulator also yields a real RTOS tick periodically when continuously late.
Solution
Core 1 owns the priority-6 emulator and priority-7 input path. Core 0 owns priority-8 I²S, priority-7 APU generation, BMI270/power/VCOM services, and the lower-priority PogopoOS UI/display loop.
Result
The task split used by the 59.7 Hz emulator / ~29.9 Hz LCD baseline is now explicit in configuration rather than implicit in the main loop.

Hardware debugging

Problem
Custom-board bring-up needs to distinguish wiring, bus, device-ID, and software-state failures across several peripherals.
Investigation
Firmware probes the TCA9555 at 0x20, BMI270 at 0x68, and BQ24295 at 0x6B, then reads identity, configuration, status, and fault registers.
Solution
Startup and system-status diagnostics report device health, button-port state, charger status/fault registers, internal RAM, and PSRAM. Dedicated on-device apps exercise controls, audio, haptics, motion, power, and display behavior.
Result
Board failures can be narrowed to a named peripheral and register set instead of appearing only as a broken UI feature.

Storage and peripheral reliability

Problem
Removable storage, I²C controls, and power-off can fail at inconvenient times: a mount can fail, a file path can exceed fixed buffers, an I²C read can time out, or a save can be interrupted.
Investigation
Drivers expose explicit error returns and counters. Storage checks mount, extension, path length, file format, and allocation limits; input tracks I²C read errors; shutdown checks USB and save state.
Solution
SD mounting never formats on failure, file paths are bounds-checked, TCA9555 reads use a 10 ms timeout with released-state fallback, gameplay save writes are deferred, and pending saves flush on app exit or shutdown.
Result
The current code has defined failure behavior for these cases instead of silently formatting storage, holding a direction, or writing saves in the emulator’s critical path.
