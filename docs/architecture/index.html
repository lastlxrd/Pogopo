System

Architecture

PogopoOS separates board-specific communication from reusable services and application behavior. The goal is a small set of understandable layers, not documentation for every source file.

Logical layers

Applications sit at the top of the system and depend on PogopoOS rather than individual chips. The launcher, settings, diagnostics, Game Boy emulator, and PogoDate runtime all enter through the same application lifecycle, so opening an app, suspending it behind the quick menu, and returning Home follow one path.

PogopoOS owns that lifecycle and gives the active application access to graphics, input, audio, storage, motion, haptics, power, and settings. Those services translate useful actions such as reading a button or presenting a frame into driver operations. Pin mappings and bus details remain below the service boundary, where SPI, I²C, I²S, SDMMC, ADC, and GPIO code communicate with the physical board.

This direction is deliberate: an application can use a device capability without reconfiguring the hardware behind it. It also keeps shutdown, save flushing, display clearing, and system overlays under one owner.

Task and core organization

FreeRTOS work is separated by latency and ownership. The current Game Boy path runs emulation and input on Core 1. Core 0 handles fixed-clock I²S output, decoupled APU generation, motion and power services, VCOM maintenance, and the lower-priority PogopoOS UI/display loop.

This split is a performance decision for the current firmware, not a permanent ABI. Changes are validated with serial timing, underrun, heap, cache, and I²C diagnostics.

Typical data flow

A button sample begins at the TCA9555, passes through the input service, and reaches only the active application. Drawing moves in the opposite direction: an application writes to the shared 1-bit canvas, then the display driver sends changed rows or a complete frame to the Sharp LCD.

Game Boy audio is generated by MiniGB APU into an internal ring buffer and consumed by a fixed-rate I²S task connected to the MAX98357A. Power-off is coordinated in the same way: the Power service starts the overlay, waits for pending saves, clears the physical display, and only then asks the BQ24295 to enter ship mode.
