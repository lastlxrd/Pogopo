# STEP11.6.27 — Noble image-backed sprite rendering

## Before

Hillslide retained its terrain and snowboarder after STEP11.6.26. Maze opened
its title and level-selection screens, and the rolling-marble sound confirmed
that level logic and accelerometer input were active. The level framebuffer,
however, showed only the full-screen dotted background: walls, holes, goal and
marble were absent.

## Cause

All 21 live level sprites had valid positions, dimensions and non-transparent
image pixels. They inherit `NobleSprite:draw()`, a hook which advances a Noble
animation when one exists and intentionally does nothing for a static sprite.
On the Playdate, assigning `sprite.image` retains normal image rendering even
when the subclass exposes this hook. PogoDate instead classified every
subclass `draw()` as a complete custom replacement, rendered the empty hook to
a transparent cache, and never drew the assigned image.

## Changes

- add the SDK-compatible no-op base `sprite:draw()` method;
- render assigned sprite images and tilemaps through their native paths even
  when a subclass inherits a `draw()` hook;
- reserve offscreen custom-callback rasterization for sprites which have no
  assigned image or tilemap;
- retain custom callback caching, image draw mode, clip, stencil, scale,
  rotation, flips and draw-offset handling;
- add live Maze framebuffer captures to the regression procedure.

## Result

The scripted Maze run now enters a live level and visibly renders its dotted
background, walls, four holes, goal and moving marble. It completes 3,000 host
ticks / 900 Lua frames with zero errors. Hillslide still completes all nine
scene tests, including 500 Training and 1,000 gameplay frames, and its separate
420-frame camera visual test passes with zero errors.

The fix is engine-level and package-independent: it follows the same
image-backed versus callback-only sprite distinction for every PDX using
Noble Engine or a similar `graphics.sprite` subclass.
