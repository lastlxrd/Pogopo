# STEP11.6.26 — camera draw-offset compatibility

## Before

STEP11.6.25 made Hillslide's hill rasterizer substantially faster, so movement
became smoother. The snowy foreground and snowboarder still disappeared after
several seconds, leaving the mountain background and HUD. A long host capture
reproduced the same failure without a Lua error.

## Cause

The game objects were not deleted. At 4.8 seconds the active scene still held
three hill objects and a live player around world x=1028. Hillslide scrolls the
world with `graphics.setDrawOffset()`, but PogoDate applied that offset only
when flushing the complete framebuffer to the LCD. Images at world x>400 had
already been clipped away before that late shift, so no pixels remained to
move into the camera viewport. This caused the exact half-slope, empty-slope
and missing-player sequence seen on Pogopo.

The same late-offset behavior also ignored vertical offsets used while
building Hillslide's dithered terrain render targets.

## Changes

- apply draw offset to image positions before source/destination clipping;
- apply it to scaled and rotated image centers without double translation;
- apply it to filled/outlined rectangles, rounded rectangles and pixels;
- apply it to lines, circles, polygons and triangles before rasterization;
- apply it to native PFT glyphs, system fallback glyphs and button symbols;
- polygon scanline spans use already translated target coordinates;
- LCD flush now uses display offset only, not the world draw offset;
- preserve `image:drawIgnoringOffset()` by cancelling the active offset;
- preserve sprite `ignoresDrawOffset` behavior and offscreen contexts.

## Result

The full Hillslide regression still opens all nine scenes and completes 500
Training plus 1,000 gameplay frames with zero Lua errors. A dedicated 400-frame
camera capture now keeps the snowboarder and generated snowy terrain visible at
frames 90, 240, 320 and 400. Before this fix frame 240 contained only the
mountain background and HUD.

This step fixes the disappearance independently from the remaining device FPS.
STEP11.6.25 handles terrain generation cost; STEP11.6.26 makes the generated
world render at the correct camera-relative position.
